02 / 07

Taking Over SSAS With No Internal Backup

One of the strongest experience stories you can tell — shows initiative, structured thinking, and risk ownership.

Your story framing "I inherited a live SSAS environment with no documentation, no previous owner available, and users who depended on it daily for reporting. My first job was to make sure nothing broke while I understood what was there — and then systematically build the knowledge base that should have existed from day one."

The situation

Zero handover

Walked into a running SSAS multidimensional cube (or tabular model) that was the backbone of management reporting — finance, supply chain KPIs, demand planning. No documentation. No prior owner to call. Users were hitting the cube daily via Excel pivot tables and SSRS reports. Any change or failure was my problem immediately.

The business risk was high: the cube was processing on a nightly schedule, SSIS packages were feeding it from multiple source systems including the ERP, and there was no staging environment — changes went straight to production.

Situation

Live SSAS cube, no docs, no backup person, users dependent daily for supply chain & finance reporting

Task

Stabilise first, understand second, document third — without disrupting live reporting

Action

Reverse-engineered the model, traced all SSIS feeds, interviewed report users, built a dependency map and a documentation baseline

Result

Full knowledge base built in 3 weeks. Identified 2 broken SSIS packages running silently. Established change control and a dev/UAT environment.

The step-by-step takeover approach

Day 1–3
Freeze and observe
No changes. Watch the nightly processing run. Note what succeeds, what warnings appear. Identify all scheduled jobs in SQL Agent touching the cube. Screenshot everything in SSMS and SSDT.
Day 4–7
Map the data lineage
Open every SSIS package. Trace source → staging → DSV → dimensions → measure groups. Draw a hand-drafted lineage map. Note the grain of each fact table, what keys join to what dimensions, and any hardcoded business logic in the SSIS transforms or SSAS calculated measures.
Week 2
Interview the users
Ask each team: which reports do you use every day? Which numbers do you trust? Which ones do you always cross-check against something else? — the last answer tells you where the model has known quality issues no one documented.
Week 2–3
Document as you learn
Build a living Word/Confluence document: data sources, transformation rules, dimension tables and their grain, measure group definitions, calculated members in MDX/DAX, known issues, scheduled jobs and their dependencies.
Week 3–4
Create a dev environment
Deploy a copy of the cube to a non-production server. This gives a safe space to test changes before production. Even a personal laptop running SQL Server Developer Edition works as a starting point.
Month 2
Establish change control
Version control all SSIS packages and SSAS project files in Git (or at minimum a network share with timestamps). No change goes to production without a tested dev version and a written change record.

Cube & tabular model design — key business logic situations

Situation: The numbers didn't match what finance expected

Business logic

A common issue when taking over SSAS cubes: the revenue or inventory figures in the cube don't match the ERP's own reports. Usually caused by three things — different date logic (transaction date vs posting date vs period close date), currency conversion applied at the wrong grain, or partial loads where SSIS was filtering out certain transaction types silently.

Approach: Take one specific number the business trusts (e.g. a monthly closing inventory value), trace it from the ERP source table all the way through SSIS and into the SSAS measure, step by step. Once you find the divergence point you have the root cause. Fix the logic, document the rule, and add a reconciliation check into the SSIS package that fails loudly if the totals drift by more than an acceptable threshold.

Situation: MDX calculated measures with undocumented assumptions

Model design

Many inherited SSAS cubes have complex MDX calculations — rolling 12-month averages, stock cover days, year-over-year % — with no explanation of what the formula represents in business terms. Someone has made an assumption about fiscal year start, working day exclusions, or which warehouse locations to include, and it's baked into the MDX silently.

Approach: For every non-trivial calculated member, write a plain-English business definition alongside the formula. Get a business user to confirm that definition is correct. This process almost always surfaces at least one formula that no longer reflects current business rules — a location was added, a product category was renamed, a fiscal calendar changed. Fixing those silently wrong calculations is often the highest-value thing a new owner can do.

SQL Server 2016 — End of Support & Migration Options

SQL Server 2016 mainstream support ended July 2021. Extended support ended July 2026 — this is an active, urgent conversation right now.

Why this matters today SQL Server 2016 Extended Support ended July 12, 2026 — effectively now. Running beyond this date means no security patches, no compliance coverage, and increasing audit risk. Any organisation still on SQL Server 2016 hosting SSAS cubes or SSIS packages needs a concrete migration plan.
Recommended
Option A

Migrate to Azure SQL / Fabric

Move the database workloads to Azure SQL Managed Instance or Azure SQL Database. Pair with ADF (replaces SSIS), Fabric Semantic Models (replaces SSAS), and Power BI (replaces SSRS). Full modernisation — no new on-prem hardware, Microsoft manages patching forever.

Option B

Upgrade to SQL Server 2022

In-place or side-by-side upgrade to SQL Server 2022 (support until 2033). Keeps the on-prem model. Lower risk short-term — SSAS, SSIS, SSRS all still work. Buys 7 years but doesn't address the strategic shift to cloud. Good if regulatory constraints block cloud now.

Option C

Azure Arc-enabled SQL Server

Register your on-prem SQL Server 2016 with Azure Arc to extend security updates for up to 3 additional years while the cloud migration plan is prepared. Useful bridge strategy — keeps you patched while the migration project is approved and resourced.

SSAS specifically on SQL Server 2016 — migration path

Multidimensional → Tabular

If still on SSAS Multidimensional

SSAS Multidimensional (MDX cubes) has no direct cloud equivalent. The migration path is: rebuild as a Tabular model first (DAX replaces MDX), then migrate the Tabular model to Azure Analysis Services or Fabric Semantic Model. Two-step, but each step is manageable.

Tabular → Fabric

If already on SSAS Tabular

The migration to Fabric Semantic Models is relatively straightforward — .bim file export from SSDT, import into Fabric. DAX measures migrate with minimal changes. The main effort is re-pointing data sources from on-prem to cloud (Synapse, ADLS, or Azure SQL).

What to say in the interview "My recommendation is a two-track approach. Track one: immediately register the SQL Server 2016 environment with Azure Arc to extend security updates — this removes the compliance risk while the migration project is being scoped. Track two: plan a 6–9 month migration to Azure, using ADF to replace SSIS and Fabric Semantic Models to replace SSAS. The SSRS reports migrate last, after Power BI is adopted by key users."

Creating Clear Documentation for SSAS, SSIS & Data Flows

Documentation is a first-class deliverable, not an afterthought. The goal: any competent engineer can pick this up cold and understand what's happening and why.

Your philosophy "Good documentation answers three questions for the person reading it: what does this do, why does it do it this way, and what breaks if it stops. If it only answers the first one, it's incomplete."

The four-layer documentation framework

Layer 1 — Architecture overview (1 page)

Start here

A single diagram showing all source systems, staging databases, SSAS model(s), and downstream consumers (SSRS, Excel, Power BI). No detail — just the map. Anyone joining the team reads this first.

Source system names + connection strings (secured) Staging DB schema overview SSAS model names & server locations Consumer list (who uses what) Processing schedule / frequency

Layer 2 — SSIS package register

Data movement

A table for every SSIS package: name, purpose, source, destination, schedule, dependencies, known issues, and last tested date. Stored in Confluence/SharePoint alongside the .dtsx files in version control.

Package name + purpose Source → target mapping Transform logic (plain English) Error handling approach SQL Agent job name + schedule Dependency order Known issues / workarounds

Layer 3 — SSAS model data dictionary

Business logic

The most important and most commonly missing layer. For every dimension, attribute, measure, and calculated measure: business name, technical name, source column, business definition, and any assumptions or exclusions baked in.

Dimension tables + grain Attribute hierarchies explained Fact table grain + foreign keys All measures with business definition All calculated members (MDX/DAX) + plain-English logic KPIs with business owner sign-off Known reconciliation gaps

Layer 4 — Operational runbook

Day-to-day ops

Step-by-step procedures for the most common operational scenarios. Written so that a junior engineer on call at 7am can follow it without calling anyone.

How to re-run a failed SSIS package How to trigger a manual SSAS process How to check processing errors in SSMS Common errors and their fixes How to deploy a change to production Escalation contacts Monthly / quarterly maintenance checklist
Tooling recommendation Layer 1–3: Confluence (or SharePoint Wiki) with diagrams in draw.io. Layer 4: A simple Markdown file in the same Git repository as the SSIS packages and SSAS project files — documentation lives with the code, so they stay in sync. Auto-generate the SSAS data dictionary using Tabular Editor's scripting capability or DMVs queried from SSMS.

Day-1 Plan — How You'd Tackle This Upon Joining

A structured, confident answer to "so what would you do in your first 30–90 days?" — shows you've thought about it before they've even offered you the role.

Opening line for this question "I'd structure the first 90 days in three phases: understand before you touch, fix the highest-risk gaps, then build for the future. The worst thing you can do is walk in and start changing things before you know what's connected to what."
Days 1–14 · Listen & Map
No changes — pure discovery
Meet every stakeholder who uses data: finance, supply chain, procurement, operations. Ask what they use, what they trust, and what they know is broken but live with. Simultaneously map all data flows: source systems → SSIS → staging → SSAS → reports. Identify every scheduled job. Locate all SSIS packages and determine if they're version-controlled.
Days 15–30 · Assess & Prioritise
Risk register + quick wins
Build a risk register: SQL Server 2016 EOL status, SSIS packages with no error handling, SSAS processing failures that go unnoticed, reports with no owner. Also identify quick wins — small data quality fixes, a broken alert that's easy to fix, a calculation that's been wrong for months. Early trust is built through small, visible improvements.
Days 31–60 · Stabilise
Fix the foundations
Establish a dev/UAT environment if one doesn't exist. Put SSIS packages and the SSAS project into source control. Add error alerting to all SSIS jobs (email on failure). Begin the documentation framework — architecture overview and SSIS package register first. Address the SQL Server 2016 EOL risk with a formal recommendation to leadership.
Days 61–90 · Propose
Modernisation roadmap
Present a clear modernisation roadmap: Azure Arc as immediate SQL 2016 bridge, phased migration to ADF + Fabric over 6–12 months, Power BI adoption alongside SSRS, and a D365 Synapse Link strategy for any ERP data. Get stakeholder alignment before any migration work begins.

Risks & Solutions

Show you've thought about what goes wrong — not just what should go right.

Risk Likelihood Impact Your solution
SQL Server 2016 EOL — no security patches post July 2026 High High Immediate: Azure Arc extended security updates. Medium-term: migrate to Azure SQL / SQL 2022 within 6 months.
SSIS packages failing silently — no alerting in place Medium High Add SQL Agent job failure notifications (email/Teams). Add row-count validation steps to each SSIS package. Create a daily processing health dashboard.
SSAS cube processing fails — users see stale data Medium High Add processing alerts. Implement partition-based incremental processing to reduce processing window. Add a "data freshness" indicator visible to users in reports.
No documentation — key person dependency / bus factor = 1 High High 4-layer documentation framework (architecture → SSIS register → model dictionary → runbook). Target: anyone can take over in 2 weeks. Version-control everything.
SSAS cube performance — slow MDX queries impacting users Medium Medium Run MDX/DAX query profiler. Add aggregations for the most-queried dimensions. Review partition strategy. Consider migrating to Tabular model (consistently faster for most query patterns).
Migration disrupts live reporting during cutover Medium High Run old and new systems in parallel for a validation period. User acceptance testing on the new Fabric model before any SSAS decommission. Phased report migration, not big-bang.
Business logic lost in migration (undocumented MDX rules) High Medium Document all calculated measures before migration begins. Business owner sign-off on every KPI definition. Reconciliation testing: compare old vs new numbers row by row for 2–3 reporting periods.
User resistance to Power BI / moving away from SSRS Medium Medium Don't force migration. Run Power BI as an addition first. Find a champion in each team. Keep SSRS running until Power BI is proven. For pixel-perfect paginated reports, use Fabric Paginated Reports — same format, low re-training.
07 / 07

If Users Are Struggling With the Existing SSAS Cube

The most practical question in any BI role interview — shows you can diagnose and fix, not just replace.

Your opening line "Before I recommend replacing anything, I'd want to understand what 'struggling' actually means — is it performance, wrong numbers, complexity, or just lack of training? The answer changes the solution completely."
Problem: Slow queries / reports timing out

Performance fix

  • Profile slow MDX queries using SQL Server Profiler or Extended Events
  • Add aggregations for the most-used dimension combinations
  • Review partition strategy — monthly partitions on large fact tables
  • Check memory allocation on the SSAS server
  • If consistently slow: migrate to Tabular model (faster for most patterns)
Problem: Wrong numbers / doesn't match ERP

Data quality fix

  • Trace one specific value from ERP source to cube output — find the divergence point
  • Check SSIS for silent row filtering or type conversion errors
  • Verify date logic — fiscal vs calendar, transaction date vs posting date
  • Review currency conversion logic in SSAS
  • Add automated reconciliation: cube total vs ERP source total, alert on drift
Problem: Too complex / users can't find what they need

Usability fix

  • Hide unused measures and attributes in SSDT (reduce clutter without deleting)
  • Rename cryptic technical names to plain business names
  • Create named sets for common filter combinations users always apply
  • Build pre-built Power BI reports on top of the cube as a friendlier front-end
  • Run a 30-min user training session on how the model is structured
Problem: Cube is beyond saving — rebuild?

When to replace, not fix

  • If the source data model is fundamentally wrong (wrong grain, missing keys) — a patch won't hold
  • If it's on SQL Server 2016 SSAS Multidimensional — the EOL case is the forcing function
  • Rebuild as a Tabular model in Fabric: cleaner, faster, Power BI-native, cloud-managed
  • Migrate in parallel — keep the old cube live until the new model is validated
  • Use the rebuild as the opportunity to document properly from day one
Closing line for the interview "My default is always: fix before replace, because a replacement that has the same undocumented logic problems is not an improvement. But when the platform is end-of-life and the architecture is fundamentally misaligned with how the business needs to report, rebuilding on a modern stack is the right call — and it's the right time to do it properly."
