What just happened

Idle

Think USB-C for AI. One plug. Many tools. You ask in English; a server does the work; the host writes the answer.

MCP is JSON-RPC 2.0 between a host-owned client and a server. First they negotiate capabilities, then the client lists tools and calls one.

Host owns policy, sampling, and conversation state. Each client is isolated 1:1 with one server. Servers never see the full chat — only the arguments the host chooses to send.

What is MCP?

Before MCP, every AI app needed a custom integration for Gmail, Slack, your database, your files. MCP is the shared plug. Write the server once; Claude Desktop, Claude Code, Cursor, and VS Code can all use it.

MCP is an open protocol (Anthropic, 2024; spec dated by version, currently 2025-11-25) for exchanging context and tools with an LLM app. It does not tell the host how to call the model. It only standardizes how context arrives: tools, resources, and prompts over JSON-RPC.

Scope is deliberately narrow: a data layer (JSON-RPC methods, lifecycle, primitives) and a transport layer (stdio or Streamable HTTP). Hosts compose many servers. Security boundary is the host — approval, redaction, and sampling stay on the client side. See the official architecture at modelcontextprotocol.io.

Three participants — click a box

Host

The AI application

Cursor, Claude Code, Claude Desktop, VS Code. Creates one client per server. Talks to the LLM. Enforces “may I run this tool?”

Client

One socket, one server

A connector inside the host. It negotiates the protocol version, lists primitives, and routes messages. It never shares memory with sibling clients.

Server

Focused capability

Local process (stdio) or remote service (HTTP). Exposes tools, resources, prompts. Can also ask the host for sampling or user input.

Host. This is the app you see. You type here. It decides which server to ask, then shows you the answer.

Host. Instantiates N clients for N servers, merges tool schemas into one model tool list, and intercepts tool calls before they hit a server.

Host. Trust boundary and UX owner. Policy (allow-list, confirmation, PII filters) lives here. A compromised server should not read sibling-server traffic or the raw system prompt.

Two layers, same messages

Transport

How bytes move

stdio — host launches a local process and talks on stdin/stdout. Fast, no network, one client.

Streamable HTTP — POST for requests, optional SSE for streams. Remote, multi-client, OAuth / bearer tokens.

Data

What the bytes mean

JSON-RPC 2.0: requests have an id, notifications do not. Methods look like initialize, tools/list, tools/call, resources/read, sampling/createMessage.

The handshake, then the work

1
initialize — versions + capabilities. If they cannot agree, hang up.
2
notifications/initialized — client is ready. No id, no reply expected.
3
tools/list (or resources/prompts) — discover schemas so the model can choose.
4
tools/call — host sends arguments; server returns a content array.
5
Model writes — the host, not the server, turns the tool result into the user’s answer.

Three server primitives

Tools

Do something

Functions with JSON Schema args. Weather, SQL, browser click. Model-initiated. Often needs user approval.

Resources

Read context

URI-addressable data: config://app, docs://runbook/{svc}. Application-initiated. Usually read-only.

Prompts

Reuse a template

Named message recipes users pick: “incident update”, “release note”. Not a tool call — a structured start.

Rule of thumb: tool = verb, resource = noun, prompt = recipe.

Clients also expose primitives the other way: sampling (server asks the host LLM), elicitation (server asks the user), roots (filesystem / URI bounds), logging.

Advertise only what you implement. tools.listChanged means you will send notifications/tools/list_changed. Sampling must stay host-gated — the server should never see an unredacted system prompt. Prefer small, composable servers over a god-server.

Same server, three altitudes

One weather capability. Junior writes the function. Mid adds schema, a resource, and a prompt. Architect designs isolation, transport, and policy.

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather")

@mcp.tool()
def weather_current(location: str) -> str:
    """Get the current weather for a city."""
    return f"{location}: 32°C, clear, humidity 41%"

if __name__ == "__main__":
    mcp.run()  # stdio — Cursor / Claude Code spawn this process

Docstring + type hints become the tool schema. You did not write JSON-RPC. The SDK did.

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather")

@mcp.tool()
def weather_current(location: str, units: str = "metric") -> str:
    """Current conditions. units: metric | imperial."""
    if units not in {"metric", "imperial"}:
        raise ValueError("units must be metric or imperial")
    temp = "32°C" if units == "metric" else "90°F"
    return f"{location}: {temp}, clear"

@mcp.resource("weather://stations")
def stations() -> dict:
    """Read-only list of stations the model can cite."""
    return {"stations": ["VIDP Delhi", "VABB Mumbai", "VOBL Bengaluru"]}

@mcp.prompt()
def travel_brief(city: str) -> str:
    """Reusable user-facing recipe."""
    return f"Write a 4-line travel weather brief for {city}."

if __name__ == "__main__":
    mcp.run()

Validate inputs. Keep resources read-only. Prompts are templates, not side effects.

# .mcp.json — host config, not server code

  }
}

# Architect checklist (this is the real work):
# 1. One client per server — weather cannot see docs traffic.
# 2. stdio for trusted local; Streamable HTTP + OAuth for remote.
# 3. Host approval on any tool that writes or leaves the machine.
# 4. Advertise only implemented capabilities (tools.listChanged, etc.).
# 5. Sampling stays on the host: server asks, host redacts, user can deny.
# 6. Least privilege: a file server gets a root, not the whole disk.
# 7. Observe: log tool name + latency, never raw secrets.
# 8. Prefer many small servers over one god-process.

The protocol is the easy part. Isolation, approval, and blast radius are the architecture.
