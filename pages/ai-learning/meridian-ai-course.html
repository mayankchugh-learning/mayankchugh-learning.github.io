Modules

Module 1

The case

Who the company is, what goes wrong without a system, and the two roles that build it.

The company slides 1-8
  • Aldermoor Industries, a fictional Hamburg machine builder, buys parts worldwide.
  • A 480,000 euro PLC order shows how one purchase raises questions for four departments.
  • Order of events: request, risk, tax, control, CFO, and only then payment.
  • The rules and people here are what the software must later apply.

Open at slide 1

The problem slides 9-17
  • One order sits in four inboxes; the answers live in PDFs that someone must know to open.
  • Four pains: slowness, hidden policy, inconsistency and the cost of a missed check.
  • Obvious fixes (a shared folder, a phone call) each solve one pain and leave another.
  • Mental model: files hold the answers, people on the phone hold the judgement.

Open at slide 9

The solution slides 18-27
  • Two helpers in one app: a document Q&A helper and a multi-specialist audit.
  • Decision rules are written down and ordered: red alert beats hold, hold beats approve.
  • Three audit scenarios cover approve, hold and escalate; anything above EUR 250,000 is flagged for sign-off.
  • The limits are stated openly; people still decide.

Open at slide 18

AI engineer slides 28-39
  • Starts from the problem, not the model, and splits it into six small jobs.
  • Search first and answer second once documents grow beyond a few pages.
  • Exact rules (the 5 percent FX check) go in code; judgement goes to the model.
  • Build the smallest thing first, check against known answers, and watch cost, time and errors.

Open at slide 28

Forward-deployed engineer slides 40-52
  • Starts from the people: observe, then measure a baseline before building.
  • Find where real information lives; when two sources disagree, ask the owner.
  • Start narrow, widen slowly, work inside the customer's rules.
  • Earn trust by making answers explainable, then hand over so the system is not understood only by its builder.

Module 2

Set up from scratch

The project folder, the tools, the packages, and where the reference repo fits. The clone URL in this module is the one I leave unchanged.

Project basics slides 1-10
  • A project is a folder of many file kinds; secrets and generated files never go into Git (.gitignore).
  • Frontend and backend talk through an API using JSON.
  • Requirements files pin exact versions so the project behaves the same everywhere.
  • Settings live outside code; one file, one job.

Open at slide 1

Your tools slides 11-20
  • Four tools are needed now: uv, Python 3.12, Git and an editor; Node and the Gemini key come later.
  • uv replaces pip plus venv in one tool and avoids the forgot-to-activate mistake.
  • Create the project, delete the generated main.py, and bring in starter files from the reference repo (the answer key).

Open at slide 11

Packages slides 21-32
  • Two requirement files: one for running, one for development.
  • Packages group into the web service, the LangChain toolkit, and storage and documents.
  • uv add installs and writes the lock file; the environment folder is disposable.
  • Use uv run so code always runs inside the environment.

Open at slide 21

Structure slides 33-41
  • The backend/ folder has a map of about two dozen small files, each named for its job.
  • Layers may only use layers below them, which keeps code testable.
  • Build order follows that dependency rule; you create empty folders and files first.

Module 3

The backbone

Settings, the API key, and how errors and logs are supposed to read. Keys stay in an env file. I do not paste a key into notes.

Settings slides 1-8
  • Hard-coded values hurt: they force code edits and leak secrets.
  • Environment variables and a .env file hold values; .env.example is the shared template.
  • One APP_MODE setting switches local versus cloud.
  • Create a free Gemini key and keep it only in .env, verified with git status.

Open at slide 1

settings.py slides 9-22
  • A 117-line file read in eight chunks: imports, typed fields with defaults, embedding and storage settings, cloud block, agent limits, validator, helper properties and one shared settings object.
  • It reports what is missing instead of failing vaguely.
  • Four quick checks and one real Gemini call prove the chain works.

Open at slide 9

Errors and logs slides 23-37
  • A small family of custom errors that the web layer later maps to clear HTTP replies (503, 422).
  • Structured JSON logging: a processor pipeline, one shared logger, output on screen and in a file.
  • Commit the backbone; the key and logs stay out of Git.

Module 4

Document Q&A (RAG)

Retrieval-augmented answers over four policy documents. When the slides say Gemini embeddings, I translate the step to the embedding model in the project I am actually running.

RAG explained slides 1-11
  • A model cannot know your private documents; RAG looks up the right page first, then answers.
  • Two stages: indexing once, then retrieval at question time.
  • Chunks, embeddings (meaning as numbers) and why keyword search can miss what meaning search finds.
  • Know the failure symptoms; each points to a file built later.

Open at slide 1

Types of RAG slides 12-24
  • Basic RAG has three weak spots; variants fix a stage before, during or after the search.
  • Multi-query, contextual compression, HyDE, decomposition, follow-up rewrite, hybrid, reranking and bigger structural ideas.
  • A symptom checklist suggests what to try first; Meridian uses three of the thirteen.

Open at slide 12

The RAG toolbox slides 25-33
  • A RAG system has eight parts; the course builds the last column of the table.
  • What to check in embedding models and vector databases; five questions for choosing a store.
  • Pick the simplest store that runs on a laptop; LangChain is the framework used.

Open at slide 25

llm and embeddings slides 34-48
  • One shared, lazily created model connection with a clear error when the key is missing.
  • extract_text normalises model replies.
  • embeddings.py follows APP_MODE; real similarity scores show unrelated text is not zero, only ranked lower.
  • Golden rule: the same embedding model must index and search.

Open at slide 34

Stores slides 49-62
  • Vector store (Chroma locally) holds numbers and text; document store keeps the original PDFs.
  • A common interface makes local-to-cloud a settings change.
  • Keep originals because the vector database is a rebuildable copy; only the basename of uploads is trusted.

Open at slide 49

Ingestion slides 63-74
  • Cut documents with a splitter that uses overlap.
  • Stable ids mean indexing twice still counts once.
  • ingest_pdf does read, fail clearly, tag source, chunk, store; a second entry point indexes everything stored.
  • Result: four sample PDFs indexed.

Open at slide 63

Retrieval slides 75-88
  • Three search modes (similarity, multi-query, compression), one prompt and one chain.
  • The system prompt makes an honest I-do-not-know possible.
  • The chain is read as and-then (LCEL pipes).
  • Start with similarity and change mode only when you can name the problem.

Open at slide 75

Lab: the four documents slides 89-96
  • Predict the five expected answers before running anything.
  • Run all five questions and read the log.
  • Commit the document Q&A.

Open at slide 89

More RAG in code (extension) slides 97-112
  • Seven ideas tested on 22 sentences: MMR, HyDE, hybrid with reciprocal rank fusion, decomposition, follow-up rewrite, model-as-judge rerank and parent pages.
  • Honest result: every variant changes results, none is free; rerank did best here and hybrid worst.
  • Add a variant only when you can name the problem it solves.

Module 5

The audit team

LangChain agents: one tool per job, prompts as job descriptions, middleware as guard-rails, then three audits. The code-reading version of this is the study workbook.

Agents and LangChain slides 1-10
  • The LangChain family: core, LangGraph underneath and more.
  • An agent loop follows a message trail: human, ai, tool, ai.
  • A team of specialists is easier to steer than one agent with every tool.
  • The supervisor is plain Python, not an AI.

Open at slide 1

Tools slides 11-23
  • A tool is a decorated function with name, docstring and typed arguments that the model sees.
  • Sanctions and tax tools ask the model; the FX tool uses live rates and an exact 5 percent rule in code.
  • Strict JSON with parsing and fallbacks; categorize_expense uses a fixed format.
  • Honest section: this demonstrates the pattern, it is not a compliance system.

Open at slide 11

Prompts slides 24-34
  • Prompts are job descriptions: role, responsibilities, decision framework, output format.
  • Output keywords are a contract the CFO prompt relies on.
  • The CFO decision rule lives in a prompt: red alert, then hold, then approve.

Open at slide 24

Middleware slides 35-44
  • Guard-rails wrap the agent loop without touching prompts or tools: limits, redaction, our own logging.
  • Order of the stack matters.
  • Demo: the same question gives different outcomes and the model never sees the email address.

Open at slide 35

The audit team slides 45-54
  • An agent equals model plus tools plus system prompt plus middleware.
  • Each specialist gets only a few tools; three phases run in order, then a CFO memo applies the rule.
  • Design choices stated plainly, including where a real sanctions database would plug in.

Open at slide 45

Lab: three audits slides 55-64
  • Predict each decision, then run three cases covering the three outcomes.
  • Read the tool log to see what the team did and how long it took.
  • Wording differs per run, the decision layout does not; commit afterwards.

Module 6

The service and the screen

FastAPI routes, logging, tests, a React screen, and running the stack locally. The course’s screen is a teaching UI. My public React apps are separate products and are not this screen.

FastAPI slides 1-11
  • Why an API: users are in a browser, code is in Python.
  • Request equals method, path and body; reply equals status code and body.
  • FastAPI and Uvicorn are the two names you type; /docs gives free documentation.
  • A tiny hello server shows validation errors (422) before the real app.

Open at slide 1

Request shapes slides 12-24
  • Schemas are four small classes that form the contract between screen and server.
  • Seven routes grouped by four routers: health, status, agent and documents.
  • Routes are thin: validate, call real code, return; upload keeps only the file name and cleans up.

Open at slide 12

The server slides 25-39
  • main.py assembles start-up, CORS and error handlers (configuration error becomes 503).
  • Run, call, then break it on purpose: missing field, wrong route, no key.
  • The RAG answer and the audit are each one HTTP call; /docs works instead of curl.

Open at slide 25

Logging slides 40-48
  • Three kinds of lines share the console; only some reach the file.
  • Levels tell the story: info, warning, error.
  • Structured logs let you list which audit tools ran and for how long.

Open at slide 40

Tests slides 49-58
  • Tests must not call Google: slow, costly and different each run.
  • conftest.py sets fake settings; test_api.py uses stand-ins.
  • Seventeen tests pass in about five seconds; they prove the plumbing, not the model quality.

Open at slide 49

The screen slides 59-70
  • A React plus TypeScript frontend with four tabs: Index Documents, RAG Q&A, Procurement Audit, System Status.
  • api.ts is the only file that talks to the server.
  • The audit progress steps are timers, which is why it can say Complete too early.

Open at slide 59

Run it all slides 71-81
  • Two ways to run: two terminals in development or one server after building the screen.
  • A six-step lab uses the whole app; run both test suites and commit.
  • Seven honest limits; Part 1 is a working local system and Part 2 moves to the cloud.

Open at slide 71
