Author byline: Mayank Chugh, Enterprise Architect · TOGAF 9.2 · IT Governance · M&A Integration, https://mayankchugh-learning.github.io/.

KEY DISTINCTION callout at the top: "Target architecture answers WHAT SYSTEMS. Target operating model answers HOW THE ORGANISATION RUNS ONCE THEY'RE LIVE. Delivering the first without the second is how a technically successful migration still fails."

COLUMN 1 — TARGET ARCHITECTURE (navy, technical iconography)
Scope: systems, platforms, data flows, integration points.
Output: diagrams, standards, a migration roadmap.
Owned by: architecture and engineering.
Answers: "What will exist, and how does it connect?"
Cargo analogy: the new warehouse management platform is specified, built and cut over successfully.

COLUMN 2 — TARGET OPERATING MODEL (gold, organisational iconography)
Scope: org structure, roles, decision rights, governance forums, processes, support model.
Output: a RACI, a defined escalation path, named owners, a runbook.
Owned by: business and operations, with architecture contributing.
Answers: "Who runs this on Monday, who decides when it breaks, and who pays for it?"
Cargo analogy: the crews know who owns which process on the new platform, who signs off a change, and who gets called at 3am.

TRIAD DIAGRAM (centre, between or below the columns): three overlapping circles labelled PEOPLE, PROCESS, TECHNOLOGY. Shade the TECHNOLOGY circle to show it is the only one target architecture covers, with a caption: "A TOM covers all three. A target architecture covers one."

CASE-STUDY PANEL (bottom, amber-bordered, kept generalised): "A cloud and data migration where the technical cutover went cleanly — target architecture delivered, on time. What wasn't defined was the operating model. Post-go-live, nobody could answer who owned the new reporting layer, so issues bounced between teams for weeks. The architecture was right. The organisation around it hadn't been designed."

Footer: "Define the operating model before Day-1, not after. Discovering it post-go-live means discovering it during an incident."

## 13. How to Read an Architecture Diagram

*Maps to video 1.5. The most practically useful item in the batch — a reference people save rather than merely like.*

```
Create a dark navy-themed infographic titled "HOW TO READ AN ARCHITECTURE DIAGRAM: THE VISUAL VOCABULARY NOBODY TEACHES YOU" using a legend/key layout, a small worked example diagram, and a common-mistakes panel. Author byline: Mayank Chugh, Enterprise Architect · TOGAF 9.2 · IT Governance · M&A Integration, https://mayankchugh-learning.github.io/.

KEY IDEA: Most people in an architecture review nod along without fully parsing the diagram on screen. The vocabulary is small enough to learn in one sitting.

LEGEND PANEL (left, laid out as a reference key, each entry showing the shape or line style beside its meaning):
Rectangle — an application or service.
Cylinder — a data store.
Cloud outline — an external or third-party system outside your control.
Solid line — a connection that exists today.
Dashed line — a planned or proposed connection.
Arrowhead — direction of data flow. An unarrowed line tells you two things touch, not which way information moves.
Swimlane or bounded box — an ownership or trust boundary. Crossing one is where security and accountability questions live.
Colour — almost always non-standard. Always read the legend rather than assuming.

WORKED EXAMPLE (right): a small, clean target-state diagram — a current-state cluster on the left, a target-state cluster on the right, and a labelled transition arrow between them. Annotate three elements with small gold callout markers pointing to: an ownership boundary, a dashed planned connection, and a directional data flow.

COMMON MISTAKES panel (bottom, red-cross list):
A diagram showing technology but no data-flow direction — it looks complete and tells you nothing about how information actually moves.
No current state shown, only target — hides the size of the gap.
No ownership boundaries — every accountability question stays unanswered.
A legend that doesn't match the diagram, usually because the diagram was edited and the legend wasn't.

Footer: "If you can't tell which way the data flows, the diagram isn't finished — no matter how neat it looks."

Hashtags: #EnterpriseArchitecture #ArchitectureDiagram #SolutionArchitecture #TOGAF #TechnicalCommunication

## 14. How Technical Proposals Actually Get Scored

*Maps to video 1.6. Genuinely underserved — almost no EA content covers the buying side of proposals.*

```
Create a dark navy-themed infographic titled "WHY GOOD TECHNICAL PROPOSALS LOSE: WRITING TO BE SCORED, NOT ADMIRED" using a scoring-rubric table, a before/after rewrite example, and a four-part proposal structure diagram. Author byline: Mayank Chugh, Enterprise Architect · TOGAF 9.2 · IT Governance · M&A Integration, https://mayankchugh-learning.github.io/.

KEY IDEA: Most RFPs are scored against a rubric by an evaluator working through a pile of submissions. The goal is not to impress. It is to be easy to score highly — which is a different writing problem.

THE FOUR-PART STRUCTURE (horizontal diagram, numbered):
1. RESTATE THE PROBLEM — in the client's own language, not yours. Proves you read it.
2. THE SPECIFIC SOLUTION — this client's problem, named systems, named constraints. Not a capability list.
3. THE RISK SECTION — what could go wrong and how it's handled. Its absence reads as inexperience, not confidence.
4. THE EVIDENCE — one relevant, comparable engagement. One good example beats five loose ones.

BEFORE / AFTER panel (side by side, red-cross and green-check):
BEFORE: "We have extensive experience delivering large-scale cloud transformation across multiple industries using industry-leading practices."
AFTER: "Your D365 estate needs to reach Azure SQL without interrupting live reporting. We'd use change-data-capture replication to run both in parallel until cutover, which removes the downtime window entirely."
Caption: "The first is unscoreable. The second answers a question the rubric asks."

SCORING REALITY table:
| What the writer optimises for | What the evaluator is doing |
|---|---|
| Sounding capable | Ticking a criterion against a number |
| Covering everything | Finding the answer to question 4b |
| Impressive prose | Scanning under time pressure, with 11 more to read |
| Breadth of experience | One relevant, comparable engagement |

Footer: "Grounded in 55+ won technical responses across aviation and retail accounts worked while at Coforge, TCS and Capgemini."

## 15. SLA, RPO, RTO — The Three Numbers

*Maps to video 3.4. Definitional, highly searched, and the feasibility angle is the part usually missing.*

```
Create a dark navy-themed infographic titled "SLA, RPO, RTO: THREE NUMBERS EVERYONE QUOTES AND FEW VALIDATE" using a timeline diagram centred on an outage event, three definition cards, and a feasibility sanity-check panel. Author byline: Mayank Chugh, Enterprise Architect · TOGAF 9.2 · IT Governance · M&A Integration, https://mayankchugh-learning.github.io/.

MAIN DIAGRAM — a horizontal timeline with a clearly marked FAILURE POINT in the centre. To the left of it, a shaded span labelled "RPO — how much data you're willing to lose", measured backwards to the last recoverable state. To the right, a shaded span labelled "RTO — how long you're willing to be down", measured forwards to service restored. Above the whole timeline, a bracket labelled "SLA — the promise you made about how often this is allowed to happen at all."

THREE CARDS beneath the timeline:
SLA — SERVICE LEVEL AGREEMENT. The commitment: "99.9% uptime." Translate it before agreeing to it — 99.9% is about 8 hours 45 minutes of permitted downtime a year; 99.99% is about 52 minutes. Those are very different systems and very different budgets.
RPO — RECOVERY POINT OBJECTIVE. Acceptable data loss, expressed in time. An RPO of 15 minutes means your backup or replication cycle must be tighter than 15 minutes. It is a statement about your replication architecture, not an aspiration.
RTO — RECOVERY TIME OBJECTIVE. Acceptable downtime before it becomes a crisis. Determines whether you need warm standby, cold restore, or full active-active — each an order of magnitude apart in cost.

CARGO ANALOGY box: "At a cargo terminal, RPO is how many scans you can afford to re-enter by hand. RTO is how long trucks can queue at the gate before the operation stops. The SLA is what you promised the airline before either happened."

SANITY-CHECK panel (gold-bordered, the practical payoff): "Ask three questions of any SLA/RPO/RTO set. Has anyone tested a restore against this RPO, or is it a number in a document? Does the RTO include detection and decision time, or only the restore itself? Does the budget match the tier — a four-hour RTO on a nightly-backup architecture is not a target, it's a fiction."

Footer: "Defining these metrics for high-availability enterprise applications was hands-on governance work — and the recurring finding was that the numbers were set long before anyone checked they were achievable."

Hashtags: #ITGovernance #HighAvailability #DisasterRecovery #EnterpriseArchitecture #SLA
```

## 16. AI FinOps

*Maps to video 4.2. AI Engineer byline.*

```
Create a dark navy-themed infographic titled "AI FINOPS: WHY GENAI COSTS BEHAVE UNLIKE ANY IT BUDGET YOU'VE MANAGED" using a cost-driver breakdown, a gateway architecture diagram, and a four-lever control panel. Author byline: Mayank Chugh, AI Engineer · Azure · GenAI · RAG, https://mayankchugh-learning.github.io/.

KEY IDEA: Traditional IT spend is provisioned — you buy capacity and it sits there. GenAI spend is consumed, per token, per user, per retry, with no natural ceiling. Budgeting built for the first model does not contain the second.

WHY IT DIFFERS panel (three short contrasts, left):
Provisioned vs consumed: a server costs the same whether or not anyone uses it. A model costs nothing until someone does, then scales with every call.
Invisible unit cost: nobody knows what one query cost, so nobody self-limits.
Silent multipliers: retries, long context windows, agentic loops calling models repeatedly — usage grows without anyone deciding it should.

ARCHITECTURE DIAGRAM (centre): multiple department boxes on the left, all routed through a single gateway box labelled "ENTERPRISE API GATEWAY", which then fans out to model providers on the right. Annotate the gateway with three functions: rate limiting, per-department cost attribution, and usage logging. Add a caption: "Without a central chokepoint, cost attribution is guesswork and rate limiting is impossible."

CARGO ANALOGY box: "One fuel account for the whole airline, with every uplift attributed to the flight that burned it. Without attribution, you know the total and nothing else."

FOUR LEVERS panel (bottom, four columns with gold icons):
MODEL TIERING — route low-stakes tasks to a cheaper model; reserve the expensive one for work that justifies it. Usually the single largest saving available.
CACHING — repeated and near-identical queries should not be re-billed.
CONTEXT DISCIPLINE — trim what gets sent. Context length is a direct cost multiplier on every call.
BUDGET ALERTS — hard per-team thresholds with a named owner, not a monthly report nobody opens.

Footer: "This is architecture-level literacy on a governance pattern — the control points an architect should know to ask about. Not a claim of having run enterprise AI FinOps personally."

## 17. Shadow AI

*Maps to video 4.3. AI Engineer byline.*

```
Create a dark navy-themed infographic titled "SHADOW AI: BLOCKING IT MAKES IT INVISIBLE, NOT ABSENT" using a cause-and-effect flow, a failed-response vs working-response comparison, and a service-catalogue diagram. Author byline: Mayank Chugh, AI Engineer · Azure · GenAI · RAG, https://mayankchugh-learning.github.io/.

KEY IDEA: Shadow AI is almost never malicious. It's friction avoidance. Someone had a deadline, the sanctioned path took three weeks, and the unsanctioned one took thirty seconds. Any response that doesn't reduce that gap will fail.

WHY IT HAPPENS flow (left, four connected steps): Employee has a real task → sanctioned tooling is slow to approve, or too restricted to help → a public tool solves it immediately on a personal account → proprietary data has now left the perimeter, and nobody in IT knows it happened.

TWO RESPONSES comparison (centre, red-cross and green-check panels):
THE FAILED RESPONSE — block public AI tools at the network. What actually happens: usage moves to personal phones and home machines. The behaviour continues, the visibility is gone, and now you can't even measure it. You have optimised for the appearance of control.
THE WORKING RESPONSE — make the sanctioned path faster than the workaround. An open AI service catalogue of pre-approved tools staff can self-serve without a ticket, plus a fast, published review route (a 48-hour legal and technical turnaround) for anything not yet listed.

SERVICE CATALOGUE diagram (right): a catalogue panel listing pre-approved tools with a green "self-serve, no ticket" marker, beside a second route labelled "not listed? 48-hour review" leading back into the catalogue. Caption: "The catalogue has to grow, or it becomes the thing people route around."

CARGO ANALOGY box: "An unsanctioned baggage cart bypassing the security gate isn't solved by catching the driver. It's solved by making the sanctioned gate faster than the shortcut."

Footer: "The question worth asking isn't 'how do we stop this' — it's 'what took three weeks that should have taken a day?'"

Hashtags: #ShadowAI #AIGovernance #EnterpriseAI #ITGovernance #DataSecurity
